D12 · the legal chroma exception

Viewport palette proposal

The viewport is the one place saturated color is allowed outside the 5 reserved status hues — everything else in the editor stays monochrome (ink / muted / line). This page proposes concrete values for the token group doc 06 §1 names but does not fix (viewport: axis X/Y/Z, grid major/minor, selection outline, gizmo hover/active, camera widget). Why RGB-convention axis colors

Every mainstream 3D tool a hired game developer already knows (Unity, Unreal, Blender, Maya, 3ds Max, Godot) uses red/green/blue for X/Y/Z. Deviating for brand consistency would cost muscle memory for no real gain — the viewport is explicitly carved out as the one place chroma is legal (D12) precisely so this convention can be honored.

  • Axis red/green loosely echo the bad/good status hues, which is fine in practice — a gizmo arm and a status badge are never adjacent or ambiguous in context, and every tool above ships this overlap already.
  • Values are tuned (not copy-pasted from the status hues) so the two token groups stay independently defined per the 06 §1 schema, even where the hue family is intentionally shared.

Why selection ≠ warn, active ≠ wait

The status hues carry reserved semantics elsewhere in the UI (warn = active work only, pulses; wait = awaiting a human). A static selection outline or a drag-active gizmo handle is neither — reusing those hues here would quietly overload their meaning. Selection gets its own cyan; the active-drag highlight reuses the universal bright-yellow DCC convention instead of inventing something novel for no reason.
